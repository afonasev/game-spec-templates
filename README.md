# Шаблоны требований к игровым функциям

Общие требования к структуре, поведению и UX игровых функций. Шаблоны помогают одной просьбой добавить знакомое меню, настройки и другие функции в новую игру или привести существующую игру к общему подходу.

Оформление выбирается для конкретной игры: шаблоны не задают палитру, шрифты, фон, художественный стиль или движок. Формат — обычный Markdown; OpenSpec и другие системы планирования могут ссылаться на документы, но не требуются для их использования.

Версия каталога: **0.3.0**. Версии отдельных пакетов указаны в их README.

| Функция | Назначение | Зависимости |

| [Базовое меню](features/menu-base/README.md) | Структура меню, мышь/клавиатура/геймпад, фокус, возврат, подсказки, компоновка и ошибки | Нет |

Все документы одной функции находятся в её директории: требования, критерии приёмки, инструкция подключения и дополнительные материалы.

## Как использовать

1. Выберите функцию в каталоге и прочитайте её README и зависимости.
2. Прочитайте `requirements.md` и `acceptance.md`: они определяют поведение и проверяемый результат.
3. По `usage.md` опишите подключение в репозитории игры: платформы, применимые возможности, значения по умолчанию и согласованные исключения.
4. Зафиксируйте версию шаблонов и точный commit этого репозитория. Для папок подключения, submodule или скопированных документов используйте закреплённую ревизию, а не неявно меняющуюся `main`.
5. Реализуйте функцию в визуальном стиле игры и проверьте применимые критерии приёмки.

Пример просьбы агенту:

> Подключи `menu-base` и `settings` из https://github.com/afonasev/game-spec-templates на согласованной ревизии. Используй визуальный стиль игры, реализуй все применимые типовые опции и сгенерируй графическую справку по игровому управлению. Зафиксируй ревизию требований, состав опций и согласованные исключения в документации проекта. Проверь результат по критериям приёмки.

Подключение не требует общей реализации UI: проекты могут использовать разные движки и компоненты, соблюдая один UX-контракт.

## Как читать требования

- **Обязательно** — правило для каждого проекта, подключившего пакет.
- **При наличии / если поддерживается** — правило становится обязательным при соответствующей возможности игры или платформы.
- **Допускается** — разрешённый вариант реализации.
- Неприменимость возможности и отклонение от применимого требования — разные вещи. Первую объясняют в описании подключения; второе требует явно согласованного решения.
- У требований стабильные идентификаторы. Проект может ссылаться на них из задач, тестов и своей системы планирования.

## Границы каталога

В каталоге есть базовое меню, настройки, установщик и обновления настольного приложения. Сохранение/загрузка игры, действие «Продолжить», лаборатория геймдизайна, подготовка матча и обновление браузерной версии остаются за пределами текущих пакетов. Упоминание их маршрутов в меню не определяет их поведение.

`updates` не зависит от `settings`: параметры обновления не меняются игроком. Проверка версии автоматическая один раз при запуске, без ручных и повторных проверок в сессии; игрок может проигнорировать предложение. Скачивание начинается после «Обновить» и не идёт во время матча; прогресс виден в меню. После проверки пакета появляется «Перезапустить». Подготовленная версия применяется бесшовно при закрытии игры или до следующего запуска. «Что нового» показывает историю версий на русском/английском из описаний GitHub Releases.

Пользовательские настройки отделены от правил матча и параметров игрового баланса. Автоматическое обновление шаблонов не меняет уже подключённую игру: переход на новую ревизию выполняется отдельной задачей с разбором отличий.

## Развитие шаблонов

Общие требования добавляются в соответствующую директорию функции. Особенности одной игры остаются в её документации. При изменении контракта обновляются критерии приёмки и версия пакета; идентификатор удалённого требования не используется для другого смысла.

## Проверки и публикация

Полный регрессионный прогон всех тестов приложения не обязателен для публикации: изменения последней версии `main` считаются уже проверенными. Для установщика и обновлений выбираются проверки затронутого поведения по diff и baseline. Незатронутые результаты можно использовать повторно с указанием версии и платформы; проверки других платформ может выполнить пользователь. Ожидающие результаты не объявляются пройденными. Полный прогон, сборка поставки и публикация выполняются только в явно разрешённом человеком scope.
