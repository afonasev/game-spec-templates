# Жизненный цикл конфигурации

Версия: **0.1.0**. Нормативные ID находятся в [requirements.md](requirements.md); этот документ объясняет общую модель.

## Состояния

| Понятие | Смысл |
|---|---|
| Default-профиль | Один основной профиль с устойчивой идентичностью |
| Сохранённая версия | Неизменяемая конфигурация конкретного профиля |
| Черновик | Изменения относительно выбранной сохранённой версии |
| Релизная отметка | Включение версии в будущий пакет; отдельна от содержимого версии |
| Релизный каталог | Профили и все их отмеченные версии, включённые в поставку |
| Активная версия | Выбранная сохранённая конфигурация для следующих игр текущей сессии |
| Снимок матча | Конфигурация, зафиксированная при запуске конкретного матча |

Видимое имя основного профиля может быть `Default`, «Релизный» или соответствовать игре. Полномочия и принадлежность поставке не определяются именем.

## Типовой путь

1. При запуске клиента активна последняя релизная версия Default.
2. Пользователь выбирает профиль и конкретную сохранённую версию. Она становится активной для следующей игры.
3. Редактирование создаёт черновик, не меняющий сохранённую и активную версии.
4. Сохранение валидного изменённого черновика добавляет версию, выбирает её и делает активной.
5. Тест или обычная игра получают точную активную конфигурацию. Уже запущенный матч сохраняет свой снимок.
6. «Сбросить на релизную версию» возвращает активный выбор к последней релизной версии Default, сохраняя историю экспериментов.
7. Следующий запуск приложения снова начинает с релизного Default, независимо от последнего выбора.

Неявное сохранение при запуске не допускается. Если черновик изменён, UI объясняет, что сохранённая версия его не содержит; доступен возврат к редактированию и явное сохранение. Любой путь, уничтожающий черновик, сначала показывает перечень теряемых изменений и запрашивает подтверждение по LAB-DRAFT-02.

## Полномочия

| Операция | Dev-клиент автора | Production-клиент игрока |
|---|---|---|
| Выбор версии из поставки | Да | Да |
| Копирование конкретной версии в новый профиль | Да | Да |
| Новые версии профилей из поставки | Да | Нет |
| Новые версии собственного профиля | Да | Да |
| Удаление дополнительных авторских профилей | Да, с подтверждением и сохранением валидных ссылок | Не разрешает удаление профилей пакета; дополнительные операции над своими данными определяет игра |
| Постановка/снятие релизной отметки | Любая сохранённая валидная версия | Нет |
| Изменение встроенного каталога установленного клиента | Через подготовку новой поставки | Нет |

Dev-полномочия предоставляются доверенным режимом разработки, а не редактируемым полем профиля. При браузерной разработке ограничение записи обеспечивает и принимающая сторона. Конкретный механизм аутентификации, адреса и форматы проект определяет самостоятельно.

## Пример релизного каталога

Есть Default с версиями 1, 2, 3 и Experiment с версиями 1, 2. Автор отметил Default@1, Default@3 и Experiment@2.

- Поставка содержит Default@1, Default@3 и Experiment@2.
- Default@2 и Experiment@1 не попадают в пакет автоматически.
- Чистый запуск dev- и production-клиента выбирает Default@3.
- Игрок может выбрать Experiment@2 и использовать его для следующих игр сессии.
- Копирование Default@1 создаёт новый профиль с одной собственной начальной версией и без релизных отметок.
- Снятие отметки Default@3 в dev меняет будущий каталог и возвращает стартовую базу к Default@1; уже выпущенные пакеты от этого не меняются.

Состояние отметок до подготовки поставки может требовать исправления. Без релизной версии Default каталог невалиден: нельзя выпускать пакет, который не способен выполнить правило стартового выбора. Нельзя молча выбрать произвольную экспериментальную версию вместо отсутствующего релизного Default.

## Хранение и обновления

Авторские dev-профили, версии и отметки имеют постоянное Git-хранилище в проекте. Player не обязан читать Git: встроенный каталог доставляется в пакете. Собственные production-профили хранятся в долговременном хранилище устройства или браузера отдельно от пакета; они не обязаны попадать в Git автора.

Установка новой версии игры сохраняет эксперименты. Для отсутствующих новых параметров используется объявленный источник поставляемых defaults. Например, у старого профиля нет `combat.projectileEffect`: новая игра дополняет его значением `spark`, сохраняя настроенную скорость снаряда. Исходный исторический снимок не переписывается под прежней идентичностью; совместимое представление может вычисляться на чтении либо сохраняться как явно обозначенная миграция. Конкретный формат не предписывается.

Изменение типа, недоступный ресурс и нарушенная связь параметров — несовместимость, а не отсутствие нового поля. Проблема объясняется, исходные данные сохраняются. Для дальнейшего редактирования можно создать совместимую копию/версию по правилам игры. Исполнение старой версии на новом runtime не обещает прежний результат без контракта совместимости.

## Дополнительные инструменты

Live-применение, preview и импорт/экспорт подключаются отдельно. Они не обходят защиту поставки, проверку данных и предупреждение о потере черновика. Выбор seed и сценария теста не обязан становиться частью профиля: проект определяет их область и способ фиксации для воспроизведения.
